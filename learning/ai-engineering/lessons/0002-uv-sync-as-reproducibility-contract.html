uv sync is a reproducibility contract

Purpose: make “it works here” mean something another machine can reproduce.

Think of a restaurant. pyproject.toml is the menu: what the kitchen promises. uv.lock is the exact purchasing sheet. .venv is today's stocked kitchen. uv sync restocks the kitchen to match the sheet.

The three states

1. Declared intent · pyproject.tomlHuman-edited Python and direct dependency requirements.
2. Exact resolution · uv.lockThe versions uv selected, including transitive dependencies.
3. Installed reality · .venv/The machine-local environment that runs our code.

uv sync reconciles these states. It creates .venv when needed, re-locks unless told not to, installs locked packages, and by default removes undeclared extras.

Why this repository starts there

Milestone 1 is test-first. Before the first domain type, a clean checkout needs one trustworthy quality path:

uv sync
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run basedpyright

For a scientific agent this is also provenance. Different numerical-library versions can make “same code and data” a different experiment. Environment identity therefore belongs beside code revision, data identity, configuration, and seeds.

Command ownership

uv add changes intentDeclare or change a dependency.
uv lock changes resolutionResolve the graph without focusing on installation.
uv sync changes installed realityMake the environment agree with project state.
uv run executes inside realityCheck the environment, then run the command.

Local development versus CI

Plain uv sync may update uv.lock. In CI, uv sync --locked should fail if metadata and the committed lock disagree. --frozen instead trusts the existing lock without checking whether it reflects new declarations.

The boundary

Syncing does not freeze data, OS libraries, provider responses, hardware, seeds, network services, or source code. It closes dependency drift; our provenance design must close the other gaps.
